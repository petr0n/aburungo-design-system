Patterns

The composed surfaces — what the components turn into once they are a screen. Everything below is running, not screenshotted: each frame is the real harness at /ui_kits/, embedded live, so a component that renders nothing here renders nothing in the app. Click into any frame and it responds.

Flows real components

ui_kits/flows/ — TSX that imports src/components and is bundled by pnpm build:flows. One registry (ui_kits/flows/registry.ts) defines every flow once; this harness and the mobile kit both render from it, so neither can drift. Every state is addressable — ?flow=kana&state=empty — which is what makes the links under each frame, and every entry in scripts/shots.mjs, possible. Two more parameters apply everywhere: ?view=desktop swaps the phone shell for a 1280 browser frame, and ?phone=375 narrows the shell for the responsive sweep.

Mobile real components

ui_kits/mobile/ — the same flows, in an iPhone 16 Pro frame (402 × 874), plus the two screens that exist only here: landing and sign-in. It reads ui_kits/flows/registry.ts too, so adding a flow adds it to both harnesses at once. This was a hand-written mirror until 2026-08-17, and it is the mirror the drift warning was written about — it shipped a landing screen whose primary CTA asked for variant="accent", a variant no Button has ever implemented, so the button rendered as bare text. Untyped JSX could not catch that; this cannot repeat.

Desktop

The product runs in a browser, and until 2026-08-21 every flow only ever rendered inside a phone — a real surface nobody had looked at. ?view=desktop puts the same screens in a 1280 browser frame. There is no separate desktop layout to keep in step: the column, not the frame, is what widens, and the stages bleed to the column, so the crest reads as a sheet of patterned paper on warm stone rather than a full-width wash. Desktop exploration hand-written mirror

ui_kits/desktop-explore.html — this one can drift. It renders ui_kits/mobile/components.jsx, in which every component is typed out a second time in browser JSX and nothing typechecks it. A component can be correct in TSX and wrong on this screen. It is one of the last two untyped harnesses in the repo; adding a component means mirroring it here by hand, in the same commit.

Responsive app shell hand-written mirror

ui_kits/app/ — the other untyped harness, and the same warning applies. It loads ui_kits/mobile/components.jsx plus its own screens.jsx through Babel in the browser, so nothing here is checked by pnpm typecheck or pnpm lint. Judge a component on the flows or mobile kit first; this is for layout only.

Composition rules

The component rules live on the Components page. These are the ones that only exist once components become a screen — each stated with the surface it governs. All of them were written after a rendered screen disagreed with the spec, which is why each says what breaks.

The crest placement rule

A full-screen state that is not showing content carries the crest. A state showing content does not. Loading, empty and error get the patterned ground — otherwise the screen is a message floating on bare stone — and they become one family, differing by their signal (spinner, hanko, Akane triangle) rather than by whether the floor is there. The lesson list carries it too; its cards are glass panes over it.

Breaks as: the crest reaching whichever four of sixteen states somebody happened to be editing. That was the state of it before 2026-08-16.

flashcard · kana · fill · lessons — every loading / empty / error state above

The Patterned Ground Rule

A bare .emboss-bg ground carries fg and fg-heading only. fg-muted is permitted; fg-subtle and fg-faint are not — unless they sit on .glass. The tile darkens what is under it, so text is judged against the darkest pixel of the pattern: 8.40:1 for fg, 6.91:1 for fg-heading, 4.66:1 for fg-muted, and 3.47:1 for fg-subtle against a 4.5 bar.

Breaks as: an EmptyState description below contrast. Lowering the tile opacity does not fix it — 4.5:1 needs roughly .16, by which point the pattern is invisible. Put the pattern behind a card and the fine print on the card.

EmptyStage · StateStage · lesson list — checked by scripts/check-contrast.mjs

One dark slab per screen

The header band is Sumi-iro. Nothing else on the same screen is near-black — the kana keyboard is Rokushō for exactly this reason, and that is a composition decision, not a keyboard decision. You can only see it on a screen that has both.

Breaks as: two near-black sections stacked, which reads as a broken layout rather than as chrome plus a keyboard.

kana practice · fill (kana channel) · every AppHeader band

The Two-Plane Rule

The book hue owns the chrome — header band, chapter headers, progress, checkpoint furniture. The situation hue stays on the cards — PhraseCard's accent prop keeps meaning which situation. Chrome and card are different planes and never adjacent, so the two readings never compete. Watch it on Book One above: the chrome is Rokushō on all four surfaces while the card accent changes with the situation twice inside one chapter.

Breaks as: the obvious "simplification" — tinting the card to match the book. That collapses the two planes and destroys the situation signal. Do not.

book-one … book-five · checkpoint · lesson list (SITUATION_ACCENT)

The Prompt Is The Product Rule

On any study surface the Japanese phrase is the largest element on screen; chrome, labels and controls step down around it. If a button is competing with the phrase for attention, the button is wrong.

Breaks as: a primary CTA that reads before the thing being studied — most easily on the fill surface, where an input, a submit and four channel switches all want to be on screen at once.

flashcard · fill · kana drill

One primary action per screen

Ai-iro ground, paper text, 44px floor, one per screen. If two buttons are both primary, the screen has not decided what it wants. The corollary on these surfaces: no hover-only affordance anywhere, because none of this is reachable by hover on the device it is designed for.

Breaks as: a landing screen with two equal CTAs — which is also the screen where a nonexistent variant="accent" once rendered as bare text in the old hand-written mirror.

landing · sign-in · every flow's action row

Per-surface taste dials

DESIGN_VARIANCE / VISUAL_DENSITY / MOTION_INTENSITY, set per surface rather than globally. Density stays low per the Muji brief and rises only where real data density exists. Variance stays low except in the two places the brief says charm belongs. MOTION_INTENSITY never exceeds 3 — every value above 3 implies scroll-driven or magnetic interaction, which a touch-first study app does not have.

Flashcard review and kana practice went 2 → 4 on 2026-08-24. The 2 was itself a correction to a global VISUAL_DENSITY: 8 written without reading the brief, and it overshot: 2 on the two surfaces a learner spends the whole session inside is not restraint, it is a wireframe. Density did not move. What moved is permission to vary form, judged on a rendered screen and not in this table.

Absent no pattern exists

Templates a product of this shape normally has, drawn rather than described — the gap is the finding. Nothing below is a component gap; each is a whole surface with no composed pattern, so the first person to need one will invent it, and it will not match. Recommended order is top to bottom: the first two block a real sign-up, the rest block a second session.

Landing — the marketing page

One exists, and that is the problem: it is in ui_kits/app/screens.jsx, the untyped mirror, built on components.jsx rather than on src/components. Nothing typechecks it and no flow owns it, so the system cannot vouch for it. The real site chrome is the app's PageShell.tsx, not anything in this package — read that before designing the replacement.

Sign in — outside the device

Only ever rendered at 402px in the mobile kit. No desktop composition, no error states (wrong password, unverified address, rate-limited), no password reset. The mobile screen is a crossfade between two panes and does not have a wide equivalent.

Book index / home

Five books exist, each with four surfaces and a checkpoint. Nothing shows all five and lets you choose one. The book lab renders five identities side by side, but that is a decision record, not a product screen — it is the closest thing here and it is not it.

Profile

No account surface at all: no name, no avatar, no history, no streak — the last one on purpose. But an account with no page to look at is still a gap, and the sign-in flow above leads somewhere that does not exist.

Settings

Nothing for the settings the flows already imply: the input channel default (romaji, kana keyboard, system IME, speech), audio and speech permissions, reduced motion, and the furigana toggle. Four channels in fill and no screen that chooses between them.

Progress over time

ScoreCard and ProgressBar exist and the taste dials give progress summary the only density above 4 in the table — but there is no surface that composes them across sessions. The one place real data density is licensed, unbuilt.
